# REFLECTION — NoOpCoder 项目反思

> 撰写于 2026-08-13，项目完成之际。
> 本文对 NoOpCoder 项目的设计、实现和过程进行全面反思。

---

## 一、核心认知：Agent = LLM + Harness

这个项目最核心的认知转变，发生在阅读课程要求的第一句话："Agent = LLM + Harness，LLM 只占一行任务决策，其余全是工程。"

在开始这个项目之前，我像大多数人一样，认为 AI coding agent 的核心竞争力在于 LLM 的能力——模型越大、越聪明，agent 的表现就越好。但这个项目让我意识到，这句话只说对了一半。一个好的 LLM 可以让 agent 做出更好的决策，但一个可靠的 agent 需要的是一个工程化的 harness 来约束、验证和反馈 LLM 的每一次决策。

类比一下：LLM 是驾驶员，harness 是汽车的安全系统——安全带、气囊、ABS、车道偏离警告。一个优秀的驾驶员可以在赛道上跑出好成绩，但安全系统才是他每天都能平安到达目的地的保障。没有安全系统的车，再好的驾驶员也不该上路。

这个认知指导了全部设计决策：每个模块都必须做到"不需要 LLM 也能测试、不需要 LLM 也能理解"。这也是为什么 MockLLMClient 是第一个被实现的核心组件——它让所有工程师在没有真实 LLM 的情况下，也能验证 harness 的每一个机制。

## 二、治理护栏：为什么是代码，不是提示词

选择治理护栏作为重点深入维度，是因为它完美地体现了"工程 > 智能"的理念。

如果我让 LLM 通过 prompt 来约束自己的行为（"请不要执行危险命令"），这本质上是一种"软约束"——它依赖于 LLM 的"理解"和"自觉"。在安全领域，软约束 = 没有约束。任何 prompt 注入攻击、模型幻觉、或者简单的"忘了"，都会让约束失效。

代码实现的护栏是"硬约束"——`RuleGuard.check({type:"shell", command:"rm -rf /"})` 永远返回 `{verdict: "deny"}`，无论 LLM 怎么想、怎么说、怎么糊弄。这种确定性是硬件安全的基础：它不是"建议不要做"，而是"不能做"。就像汽车的刹车不是"建议你停下来"，而是物理上阻止车轮继续转动。

三层架构的设计（RuleGuard → SandboxGuard → HITLGuard）也体现了分层的工程思想：
- **RuleGuard** 是快速拒绝层——规则表匹配，O(n)，毫秒级
- **SandboxGuard** 是边界检查层——路径规范化 + 命令过滤，需要路径解析
- **HITLGuard** 是最后防线——人工确认，只在"ask"规则时才触发

这种"快速拒绝优先，人工确认兜底"的设计，在安全系统中是经典模式。它让我意识到，很多"AI 安全"的问题，其实可以用传统的安全工程方法来解决——不需要 AI 理解什么是危险，只需要规则表、路径规范化、状态机。

## 三、Mock 驱动开发：最好的测试就是不需要 LLM 的测试

课程要求"A.4(C) 所有机制必须可通过 mock LLM 测试"。这个要求看似简单，但在实践中，它迫使你做出正确的架构设计。

如果 LLM 调用是硬编码在 Agent 循环中的，你无法 mock 它。如果 Guard 检查是 prompt 的一部分，你无法 mock 它。如果 Feedback 依赖于 LLM 分析测试结果，你还是无法 mock 它。

Mock 驱动开发本质上是一种**依赖反转**：所有依赖 LLM 的行为必须是可替换的。这迫使你将 LLM 视为一个"数据源"（输入：messages → 输出：content），而不是一个"智能体"。LLM 被降级为 harness 的一个接口，而非核心。

这种设计的好处是显而易见的：
1. **开发效率**：不需要真实 API 调用就能开发所有机制
2. **测试可靠性**：MockLLM 的输入输出是确定的，测试结果也是确定的
3. **架构清晰**：LLM 和 harness 之间的边界被接口明确定义
4. **成本控制**：300 元额度完全够用，因为绝大部分开发不需要真实 API

当然，这也意味着真实 LLM 集成测试被压缩到了最后阶段。如果 GLM-5.2 的 JSON 输出格式不稳定，最后的集成可能会遇到问题。但好在，ActionParser 的重试机制和错误回灌设计，已经为这种情况做好了准备。

## 四、反馈闭环：让 harness 有了"眼睛"

反馈闭环是 harness 中最容易被低估的组件。表面上，它只是"写完代码后跑一下测试"。但实际上，它解决了 agent 最核心的问题：**如何知道自己的行为是否正确**。

在传统的 agent 设计中，LLM 输出一个动作，harness 执行它，然后 LLM 做下一个决策。这个流程缺少一个关键环节：验证。LLM 可能写了一段有 bug 的代码，但如果没有反馈，它不会知道这件事，会继续执行后续步骤，最终导致任务失败。

反馈闭环的设计要点：
1. **触发条件**：只在 `changedCode === true` 时触发——避免每次工具调用都跑测试的性能浪费
2. **独立于工具**：反馈不是 `run_tests` 工具（那是 Agent 主动请求的），而是 harness 自动触发的"安全网"
3. **多维度**：测试 + Lint + 类型检查，三个维度覆盖代码质量的不同方面
4. **可 Mock**：MockSensor 允许在无需真实代码库的情况下测试反馈闭环

这个设计让我意识到，一个好的 harness 不是在 LLM 和工具之间做"传话筒"，而是要对 LLM 的每一次输出进行**验证**和**反馈**。这正是"软件工程"和"提示工程"的区别——前者用代码验证，后者靠祈祷。

## 五、工具设计：changedCode 的语义精确性

一个小小的 `changedCode: boolean` 字段，背后是大量的设计思考。

`glob` 和 `grep` 的 `changedCode` 是 `false`——它们只读不写。`write_file` 的 `changedCode` 是 `true`——它明确修改了代码。`shell` 的 `changedCode` 需要检测——工作区是否有文件变化。`run_tests` 的 `changedCode` 是 `false`——测试只验证不修改。

这个字段的精确语义，影响到了反馈闭环的触发逻辑。如果 `run_tests` 的 `changedCode` 被错误地设为 `true`，那么每次 Agent 主动运行测试后，harness 又会自动触发一轮反馈，形成无限循环。如果 `write_file` 的 `changedCode` 被错误地设为 `false`，那么写完代码后永远不会触发反馈，Agent 无法知道自己的代码是否正确。

这个细节让我学到了：**在 agent 架构中，每个字段的语义都需要精确理解，一个错误的值可能导致整个系统的行为异常**。这和传统软件开发一样——类型安全不是装饰品，而是防御 bug 的第一道防线。

## 六、记忆系统：恰当的最小化

记忆系统被标注为"最低实现"——JSON 文件持久化，关键词匹配检索。很多人可能会问：为什么不做一个更复杂的 RAG 系统？为什么不使用向量数据库？

答案是：**在有限的时间和资源下，选择在哪里投入精力是最重要的工程决策**。

治理护栏值得深入——它直接关系到安全性，而且有明确的工程深度可量化。记忆系统虽然也重要，但一个简单的、能工作的实现已经满足"最低可运行"的要求。课程允许在 6 个维度中选择 1 个深入，明确了这个取舍。

这种"有意识的最小化"和"无意识的简陋"是完全不同的。前者是经过深思熟虑的取舍，后者是敷衍了事。在备忘录中明确标注"最低实现"，正是前者的体现。

## 七、AI 辅助开发：Superpowers 方法论的实践

这个项目使用了 Superpowers 方法论：brainstorming → writing-plans → subagent-driven-development → TDD → code-review → finish。在整个过程中，AI 扮演了多重角色：

1. **设计顾问**：在 brainstorming 阶段，AI 帮助分析需求、识别风险、生成设计文档
2. **计划生成器**：在 writing-plans 阶段，AI 将设计文档转化为可执行的 26 个任务
3. **代码生成器**：在 subagent-driven-development 阶段，AI 按 TDD 流程生成每个模块的代码
4. **代码审查者**：在 code-review 阶段，AI 检查代码质量和一致性
5. **文档编写者**：在 finish 阶段，AI 生成交付文档

但 AI 不能替代的是：
1. **架构决策**：哪些设计选择是合理的，这是人的判断
2. **需求理解**：理解课程要求中的隐含需求，需要领域知识
3. **质量把关**：AI 可能生成能通过测试但架构不合理的代码
4. **取舍权衡**：在有限资源下做正确的取舍，是工程师的核心能力

## 八、不足与改进

### 8.1 当前不足

1. **真实 LLM 集成测试不足**：由于时间和额度限制，真实 LLM 的集成测试被压缩了。虽然 MockLLM 测试覆盖了所有机制，但 GLM-5.2 的 JSON 输出可能仍然不稳定。
2. **记忆系统过于简陋**：关键词匹配在大规模场景下效果很差。如果项目继续发展，应该考虑引入 embedding + 向量检索。
3. **路径规范化在 Windows 上的行为**：虽然 `path.resolve` 和 `path.normalize` 是跨平台的，但 Windows 盘符和 Linux 根目录的差异可能导致边界情况。
4. **缺少 Web UI**：纯 CLI 工具对非技术用户不够友好。
5. **错误恢复不够智能**：当前的错误处理是"回灌错误信息让 LLM 重试"，但 LLM 可能不理解错误信息的含义。

### 8.2 可能的改进方向

1. **引入 RAG 记忆系统**：使用 embedding 模型 + 向量数据库实现语义检索
2. **增加更多 Sensor**：code coverage、performance benchmark、security scan
3. **支持更多 LLM 提供商**：Anthropic、Google Gemini、本地模型
4. **增加 Agent 间通信**：多个 Agent 协作完成复杂任务
5. **Web Dashboard**：可视化 Agent 的每一步决策、工具调用和反馈结果

## 九、总结

这个项目让我对 AI agent 的工程实现有了全新的理解。最重要的收获是：**AI agent 的可靠性，不取决于 LLM 有多聪明，而取决于 harness 有多坚固**。

一个只有 100 行代码的 harness，可能比一个 10000 行的 prompt 模板更可靠。因为代码是确定的、可测试的、可验证的，而 prompt 是概率性的、难以测试的、不可验证的。

如果让我用一句话总结这个项目，那就是：**最好的 AI 安全系统，是那些不需要 AI 来执行的安全系统**。治理护栏不需要 LLM 理解什么是危险，路径规范化不需要 LLM 判断什么是合法路径，反馈闭环不需要 LLM 分析测试结果。每一个安全机制都是一段确定的、可测试的代码——这才是"工程"的本质。
